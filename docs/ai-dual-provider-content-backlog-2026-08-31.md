## Воркстрим A — TSP / Suggest / Distance Matrix для AI-подбора маршрута

**Статус (2026-08-31): TSP-переупорядочивание реализовано.** Новый порт
`route_builder/application/tsp.py` (`TspProvider`, `TspOrderResult`,
`TspError`), адаптер `infrastructure/two_gis_tsp.py`
(`TwoGisTspProvider` — async create+poll VRP task API: 2ГИС TSP оказался не
одним синхронным вызовом, а `POST .../logistics/vrp/2.0/create` +
поллинг `GET .../logistics/vrp/2.0/status`, с ограниченным бюджетом
ожидания 5с и best-effort fallback на исходный порядок при любой ошибке/
таймауте), стаб-провайдер по умолчанию (`tsp_provider=stub`), новая
настройка `TSP_PROVIDER`/`TWO_GIS_TSP_DAILY_CALL_BUDGET`. Врезано в
`generate_service.generate_route()` сразу после `pick_places_for_params`,
до создания proposal — оптимизированный порядок становится каноническим
для всего нижестоящего (карточка, `RouteStop.position`, геометрия), без
рассинхрона. 20 новых unit-тестов (`test_two_gis_tsp.py` — контракт HTTP,
`test_generate_service_tsp_wiring.py` — reorder/fallback), `mypy --strict`
и `ruff` чистые, полный `tests/unit/` (375 тестов) зелёный.
`tsp_provider` остаётся `stub` по умолчанию — включение `2gis` в проде
требует отдельного шага (см. «Что делать дальше» ниже).

**Статус (2026-08-31, продолжение): Distance Matrix реализован.** Новый порт
`application/distance_matrix.py` (`DistanceMatrixProvider`,
`DistanceMatrixResult` с per-pair `distance_meters`/`duration_seconds`,
`None` вместо выдуманного числа при недостижимой паре — например
`ROUTE_NOT_FOUND`), адаптер `infrastructure/two_gis_distance_matrix.py`
(`POST /get_dist_matrix` — единственный из трёх новых сервисов оказался
синхронным одиночным запросом, как обычный Routing API, без поллинга).
Врезано в `tool_registry._find_places_near_point` (инструмент AI-чата
«найди места рядом с точкой»): один batched-вызов (1 источник — точка
запроса, до `_MAX_PLACES`=8 целей — уже одобренные кандидаты), добавляет
`travel_duration_min`/`travel_distance_m` к каждой карточке места — то, чего
не было вообще (раньше AI видел только текстовое совпадение и
PostGIS-сортировку по прямой). Best-effort: заглушка по умолчанию
(`DISTANCE_MATRIX_PROVIDER=stub`) не трогает БД вообще (явная проверка перед
любым запросом координат — не тратим лишний DB round-trip, когда провайдер
всё равно ничего не вернёт), любая ошибка 2ГИС — молча пропускает
обогащение, не ломает сам инструмент. 10 новых unit-тестов (контракт HTTP +
attach/fallback-логика), `mypy --strict`/`ruff` чистые, весь `tests/unit/`
(385 тестов) зелёный.

**Что делать дальше по этому воркстриму:** Suggest API (автодополнение
поиска) — единственный оставшийся сервис. Важная оговорка, обнаруженная при
ресёрче контракта: в отличие от TSP/Distance Matrix, для Suggest **нет
готовой точки врезки** — в бэкенде вообще не существует отдельного
поиско-эндпоинта (мобильный экран поиска фильтрует уже загруженный каталог
локально, а `search_places`-инструмент AI ищет по нашей БД текстом, не по
2ГИС). Реалистичное применение — не «поиск по каталогу через 2ГИС» (это бы
дублировало наш собственный каталог чужими данными), а **нормализация
свободного текста города/локации** в AI-чате: пользователь печатает
«Кача» или опечатку — Suggest помогает распознать канонический топоним
до вызова `search_places(city=...)`. Это отдельная небольшая, но всё же
новая интеграционная точка (не расширение существующего инструмента, а
новый шаг в извлечении slot'а `city`), и её стоит спроектировать отдельно,
а не пытаться воткнуть по аналогии с TSP/Distance Matrix.

**Контекст:** демо-ключ 2ГИС почти не используется за пределами Places/
Static/Routing (44/1000, 50/30000, 53/1000). Свободны: Suggest, Distance
Matrix, TSP — все по 0/1000.

**Куда именно встраивать:** `route_builder` module, инструментальный слой AI-
чата — `tool_registry.py:204 prefetch_context` и соседние `tool_*` вызовы,
которые уже готовят `place candidates` для LLM (`search_places`).

- **TSP API** — когда пользователь через AI-чат или ручной конструктор
  добавляет точки в произвольном порядке, прогонять набор через TSP API и
  предлагать оптимальный порядок обхода, а не порядок добавления. Встроить
  как отдельный `tool_*` в `tool_registry.py`, вызываемый на шаге
  подтверждения точек (`confirmed_fields`), не на каждое сообщение — иначе
  быстро съедим 1000 запросов.
- **Distance Matrix API** — вместо N последовательных Routing-вызовов при
  сравнении кандидатов (например, «какие места ближе всего к уже выбранным
  точкам») — один batched-запрос. Также годится для `search_places` —
  ранжировать кандидатов по реальному дорожному расстоянию, а не
  по прямой (текущее поведение quality gate явно помечает
  haversine-эвристику как `synthetic=true`).
- **Suggest API** — автодополнение в поиске мест внутри AI-чата и в обычном
  поиске (`search`/`in_place_search`) — не бэкенд AI-фичи как таковой, но тот
  же ключ и тот же budget guard.

**Бюджет и защита от прожорливости:** переиспользовать уже описанный в
2gis-personalization-offline-plan паттерн — `max_requests`, dry-run,
остановка на 80% лимита, alert. TSP/Distance Matrix вызывать только на
явные пользовательские действия (подтверждение точек, открытие экрана
сравнения), не на каждый LLM-turn.

**Тесты:** контрактные фикстуры на malformed/429/timeout ответ (как для
Routing), plus unit-тест, что TSP-подсказка не переопределяет точки, явно
закреплённые пользователем (`confirmed_fields`).

## Воркстрим B — AI dual-provider: Gemini API + локальная модель

**Статус (2026-08-31): реализовано.** `GeminiProvider` (`infrastructure/
gemini.py`) поверх Google Generative Language REST API, тот же контракт
`AIPlanningProvider`, что и у `LMStudioProvider` — общий системный промпт
вынесен в `application/prompts.py`, чтобы не разъезжался между провайдерами.
Подключён в `ai_factory.py` по значению `AI_PROVIDER=gemini`.

**Модели — проверено по актуальной документации Google (2026-08-31, не по
знаниям модели, у которой срез январь 2026):** дефолт `gemini-3.7-flash`
(сейчас GA/latest), цепочка фолбэков `gemini-3.6-flash → gemini-3.5-flash →
gemini-2.5-flash` (`GEMINI_FALLBACK_MODELS`). При 429 (упёрлись в лимит)
`GeminiProvider._generate` **автоматически переключается на следующую
модель в цепочке** — ровно то, что просил пользователь («стараться
пользоваться самыми новыми, при лимите быстро переключаться»). Любая
другая ошибка (не 429) НЕ каскадит на остальные модели — переключение
моделей не чинит некорректный запрос или таймаут. Список моделей у Google
меняется часто — эти значения стоит сверять перед продакшн-включением, не
считать зафиксированными навечно.

**Runtime-переключатель — новая инфраструктура, как и предполагалось.**
`ai_provider` был статическим env var за `@lru_cache`, поэтому под
переключатель добавлена отдельная минимальная таблица `runtime_settings`
(generic key/value, не одна таблица на флаг — под будущие тумблеры из
Workstream E) — миграция `0047_runtime_settings`, применена и проверена
на локальной БД (`alembic downgrade`/`upgrade` туда-обратно, ✅).
Сервис `runtime_config/application/service.py` читает БЕЗ кэширования:
`effective_ai_provider_settings()` подставляет `ai_provider` из БД поверх
статических настроек прямо перед вызовом `get_ai_planning_provider` в
`session_service.py` — смена в админке подхватится следующим же ходом чата,
без рестарта backend. Любая ошибка чтения БД / некорректное значение —
тихий fallback на статический env-дефолт, чат не падает.

**Ещё не сделано (осознанно, не входит в эту сессию):** сама форма/страница
в SQLAdmin для записи `runtime_settings` — это Workstream E (раздел
«Конфигурация» + доработка sidebar). Сейчас переключатель работает только
через прямую запись в БД (`set_runtime_setting()` уже готов и протестирован,
UI-обёртки ещё нет). Персонализация чата (Workstream C) поверх
существующего preferences-профиля тоже не начата.

Тесты: `test_gemini.py` (10, включая контракт fallback-цепочки: fallback на
429, НЕ-фолбэк на прочих ошибках, дедуп цепочки моделей),
`test_runtime_config_service.py` (4, override/fallback-на-БД-сбое). Весь
`tests/unit/` — 399 тестов, зелёные. `mypy --strict`/`ruff` по всему `src`
чисто.


**Что уже есть (важно — многое из просимого уже спроектировано):**

- Провайдер-абстракция уже есть: `AIPlanningProvider` Protocol
  (`route_builder/application/ai.py:47`) с `probe()`/`chat_turn(...)`,
  диспатч по `settings.ai_provider` в `infrastructure/ai_factory.py:15`.
  Сейчас реализованы только `mock` и `lmstudio` (локальная модель через
  OpenAI-совместимый HTTP-клиент, `infrastructure/lm_studio.py`).
- **`gemini` уже объявлен как значение `AIProvider` enum** (`config.py:31-35`)
  и переменные под него уже в `.env.example:36-46`
  (`GEMINI_API_KEY`, `GEMINI_MODEL`) — но адаптер никогда не был написан,
  `ai_factory.py:31` кидает `RuntimeError` для всего, кроме mock/lmstudio.
  Документы (`ai-route-planning-architecture.md`, ADR-006) подтверждают:
  Gemini-стадию планировали и сознательно отложили в пользу self-hosted
  LM Studio.
- Значит, добавление Gemini — это **написать `GeminiProvider(AIPlanningProvider)`
  + завести его в `ai_factory.py`**, без изменения интерфейса и без изменений
  в mobile (роутер `route_match_repository.dart` работает через REST и не
  знает, какой провайдер отвечает).

**Что нужно сделать:**

1. `GeminiProvider` — реализация `chat_turn`/`probe` поверх Gemini API
   (`google-generativeai` или прямой HTTP), с маппингом ролей
   (Gemini использует `user`/`model`, у нас `user/assistant/system`) и
   system-prompt эквивалентом текущего `lm_studio.py:28-55`.
2. Ключ `GEMINI_API_KEY` — только в backend `.env`, никогда в мобильный
   бандл, логи, коммиты (тот же режим, что и `TWO_GIS_API_KEY`).
3. Обработка отказов: таймаут, rate-limit 429, невалидный ответ — такой же
   typed-error контракт, как у Routing-провайдера, чтобы чат не падал молча.
4. Explicit budget/cost guard — Gemini API платный за пределами free tier,
   нужен лимит запросов и алерт, аналогично 2ГИС budget guard.

**Переключение провайдера — сейчас статический env var, не runtime:**

`config.py:84` — `ai_provider` читается через `get_settings()` с
`@lru_cache`, то есть процесс закэширован при старте. Runtime-переключаемого
хранилища настроек (DB-backed feature flag) в бэкенде вообще нет — искал,
ничего похожего не нашёл. Значит переключатель «в настройках админки»
требует новой инфраструктуры, не просто галочки в существующей вьюхе:

- Новая таблица (например `app_runtime_setting`: `key`, `value`,
  `updated_at`, `updated_by`) **или** минимальный `AiProviderSetting` с
  единственной строкой — второе проще и достаточно для одного флага.
- Сервис поверх неё, который **не использует `@lru_cache`** (или явно
  инвалидируется при записи), чтобы смена в админке подхватывалась без
  рестарта backend-процесса.
- SQLAdmin-вьюха / кастомная страница в разделе конфигурации (см. Воркстрим
  C — тот же заход, что и для sidebar) с select `mock | lmstudio | gemini`
  и, возможно, per-provider healthcheck (`probe()` уже есть в интерфейсе —
  можно дёрнуть перед сохранением, чтобы не переключить на нерабочий
  провайдер вслепую).
- Env var остаётся как **fallback/default**, если runtime-настройка не
  задана — не убираем совсем, чтобы деплой без миграции не ломался.

**Личный момент, который надо решить явно:** нужно ли пользователю видеть,
какой ИИ ему отвечает (локальный/облачный)? Не обязательно для MVP
переключателя, но стоит заложить поле в `RoutePlanningMessage.payload`
на будущее (какой provider сгенерировал ответ) — дёшево сейчас, дорого
добавлять задним числом для аналитики/дебага.

## Воркстрим C — Персонализация внутри AI-подбора

**Статус (2026-08-31): реализовано.**

- **Прайор из профиля в чат** — `session_service._persisted_preferences_prior()`
  читает те же поля `User`, что уже использует soft-scoring ranker каталога
  (`preferred_categories`, `preferred_difficulty`, `travels_with_kids`,
  `travels_with_pets`), и подмешивает их в `tool_context["user_preferences_prior"]`
  на каждый ход чата. Промпт (`prompts.py`, пункт 10) явно говорит модели:
  это подсказка из прошлых сессий, не факт этого разговора, текущее явное
  высказывание пользователя всегда важнее. Вторая система персонализации не
  заводилась — источник данных общий с каталожным ranker'ом.
- **Больше явных параметров в чате** — `avoid_crowds` (уже был в
  `_CONFIRMABLE_FIELDS`/`RouteMatchParamsIn`, но не имел ни тумблера, ни
  упоминания в промпте) получил свой `ToggleBlockOut` рядом с `with_children`/
  `with_pets`, обработку в `_control_patch`, и явно назван в системном
  промпте как допустимый ключ `constraint_patch`. `with_pets` тоже добавлен
  в промпт явно (тумблер уже существовал, просто модель не знала, что может
  его предлагать).
- **Кросс-сессионная память с явным подтверждением** — новое действие
  `save_preferences` (`chat_actions.py`, `_ACTION_CATALOG`), новый flow-ветвь
  в `session_service.post_message`, новый сервис
  `identity/application/chat_preferences.py::apply_chat_preferences()` —
  пишет в `User` **только явно подтверждённые в ЭТОЙ сессии** поля
  (`confirmed_fields`, не весь `constraints` — черновик формы никогда не
  утекает в профиль), идемпотентно (не сообщает об «изменении», если
  значение совпадает с уже сохранённым). Модель может сама предложить это
  действие через `action_ids`, но не чаще раза за сессию и только после ≥2
  подтверждённых полей (промпт, пункт 11) — не давит на пользователя.

Тесты: `test_chat_preferences.py` (6, включая «черновик без confirmed_fields
не пишется» и идемпотентность), `test_session_helpers.py` (+2 на prior),
`test_chat_actions.py` (+2). Живой end-to-end тест на реальной БД —
`test_save_preferences_action_persists_to_profile` в
`tests/security/test_route_planning_sessions_security.py`: создаёт сессию с
одним неподтверждённым полем (`with_pets` в params, но не в
`confirmed_fields`), подтверждает через `save_preferences`, проверяет через
`GET /api/v1/me`, что записались только подтверждённые поля, а
неподтверждённое — нет; второй вызов `save_preferences` корректно отвечает
«нечего запоминать» (идемпотентность). Весь `tests/unit/` (408 тестов) и
профильный кусок `tests/security/` — зелёные, `mypy --strict`/`ruff` по
`src` чисто.


**Что уже есть:** `constraints` (city, pace, interests, transport_mode,
duration, people, budget, season) и `confirmed_fields` — но это
**сессионный** контекст, не накопленный профиль. `tool_registry.py`
подмешивает сезонные рекомендации и RAG-хиты, но нет ничего похожего на
персистентный профиль предпочтений пользователя, который бы подхватывался
в новую сессию автоматически.

Отдельно уже существует soft-scoring персонализация каталога
(`2gis-personalization-offline-plan-2026-08-28.md`, секция 5) — explicit
preferences, decay, exploration slots. AI-чат её **не использует** сейчас
(секция 5.3 того же документа: «AI не ранжирует напрямую… получает только
quality-approved candidates», но не сказано, что видит preferences юзера).

**Что добавить:**

- В `prefetch_context`/`tool_registry.py` подмешивать уже существующий
  preferences-профиль пользователя (тот же источник, что и ranker
  каталога) как **prior**, а не жёсткий фильтр — ровно тот же принцип
  силы сигналов, что уже описан в разделе 5.2 GIS-плана
  (`current request > explicit preferences > …`). Не изобретать вторую
  систему персонализации рядом с уже существующей.
- Добавить в `constraints`/промпт больше явных параметров, которые
  пользователь может задать в диалоге: бюджет по категориям (не только
  общий), физическая подготовка/ограничения (уже частично есть — kids/pets
  в каталожной персонализации, в AI-констрейнтах пока нет), предпочтение
  «маршрут без машины/только пешком», желаемая плотность точек в день.
- Кросс-сессионная память: если пользователь однажды указал в чате
  «не люблю толпы» или «путешествую с детьми» — сохранять это в тот же
  preferences-профиль (с явным подтверждением, не тихой записью — уже
  сформулированное правило в GIS-плане 5.1: «не записывает preferences без
  явного подтверждения» — переиспользовать, не ослаблять).

## Воркстрим D — Контекст переписки между локальной ИИ и Gemini

**Важная находка: то, чего ты опасаешься, в основном уже решено
архитектурой.** Хранение истории — на уровне приложения, не провайдера:
`RoutePlanningSession`/`RoutePlanningMessage` (`infrastructure/models.py:92,
119`) хранят полный тред в БД независимо от того, какой LLM отвечает.
`session_service.py:102 llm_history_stmt()` берёт последние 12 сообщений
(с исключением crisis/injection-флагнутых), `lm_studio.py:199` ещё раз
бэкает до 12 перед отправкой в модель. Это провайдер-агностично: тот же
метод сборки истории будет работать и для `GeminiProvider`, если он
реализует тот же `AIPlanningProvider.chat_turn(history, …)`.

**То, что реально нужно проверить/доделать при добавлении Gemini:**

- Формат ролей — Gemini ожидает `user`/`model`, у нас `user/assistant/
  system` в БД. Маппинг делается один раз внутри `GeminiProvider`, не
  требует миграции схемы.
- System-prompt эквивалент — у Gemini system-инструкция передаётся иначе,
  чем в OpenAI-совместимом формате LM Studio; перенести логику из
  `lm_studio.py:28-55`, не переизобретать её.
- **Переключение провайдера мысли пользователя** — если человек начал диалог
  на локальной модели, а админ на середине переключил `ai_provider` на
  Gemini глобально (Воркстрим B), новый провайдер получит ту же историю из
  БД (12 последних сообщений) и продолжит разговор — контекст не потеряется
  на уровне данных. Стоит явно предупредить в UI/логике, что стиль ответа
  может ощутимо смениться (разные модели), но не как баг, а как ожидаемое
  поведение при смене движка.
- Единственный сценарий, где контекст реально может потеряться — если для
  Gemini понадобится **отдельный формат** истории (например, свой
  `conversation_id` на стороне Google для caching/tuning). Пока не
  проектируем под это — обычный stateless chat-completions запрос с полной
  историей в каждом вызове работает одинаково для обоих провайдеров и
  ничего специфичного у Gemini не требует.

**Вывод:** отдельной работы над «сохранением контекста для API-провайдера»
не нужно — она входит в Воркстрим B (просто реализовать `GeminiProvider`
корректно, используя тот же history-параметр). Не заводить отдельный
workstream под это, чтобы не задваивать работу.

## Воркстрим G — Новая модель «Блог / Рецензия» (не путать с RouteReview)

**Важно — уже проверено, чтобы не задвоить:** `RouteReview`/`PlaceReview`

**новый, более тяжёлый контент-тип поверх них**, не замена: полноценная
статья с блочной структурой (текст + картинки вперемешку), опциональной
привязкой к конкретному маршруту/локации, и **собственными**
обсуждениями/отзывами внутри (то есть обсуждение статьи ≠ обсуждение

### G.0 — Продуктовые решения, которые нужно подтвердить до старта

Это не блокеры для написания кода (ниже — разумные дефолты, взятые из уже
существующих паттернов проекта), но их стоит явно проговорить, а не
молча зашить в реализацию:

1. **Можно ли редактировать статью после публикации?** Дефолт: да, но
   правка возвращает статью в `pending_review` (тот же паттерн, что уже
   есть у отзывов — `ensure_own_editable_review`/`upsert_review`
   позволяет редактировать только пока отзыв не прошёл модерацию строгим
   образом; для статьи логично разрешить правку в любой момент, но
   каждая правка после первой публикации уходит на повторную модерацию,
   иначе автор сможет подменить текст после того, как его одобрили).
2. **Один автор — сколько статей?** Дефолт: без лимита на количество,
   но с суточным rate-limit на создание (как `route_generation_quota` у
   генератора маршрутов) — 3 черновика в сутки, чтобы не заспамили ленту.
3. **Черновик перед отправкой на модерацию — нужен ли save-as-draft, или
   отправка сразу на модерацию по кнопке «Опубликовать»?** Дефолт:
   отдельный статус `draft` (виден только автору, не проходит модерацию,
   не считается в `reviews_written`/`articles_written`-статистике) →
   автор жмёт «Отправить на модерацию» → `pending_review` → `published`/
   `rejected`. Это на один статус больше, чем у отзывов, потому что
   статья пишется дольше одного присеста — отзыв на 2000 символов можно
   написать и отправить сразу, статью с блоками — нет.
4. **Максимум блоков / картинок / общий объём текста?** Дефолт по
   аналогии с отзывами (там `_MAX_REVIEW_IMAGES = 6`, `body` до 2000
   символов): до 20 блоков, до 12 изображений на статью, каждый текстовый
   блок до 4000 символов (не 2000 — это не короткий отзыв, а статья),
   заголовок до 120 символов.
5. **Может ли статья ссылаться на несколько маршрутов/локаций сразу, или
   только на один?** Дефолт: только один (`related_route_id` ИЛИ
   `related_place_id`, не оба сразу, оба nullable) — на первой версии
   не усложняем; если понадобится «статья про поездку по трём точкам» —
   это расширение на будущее (доп. таблица many-to-many), не блокер для
   v1.
6. **Видны ли статьи неавторизованным пользователям (как каталог
   маршрутов) или только залогиненным?** Дефолт: как каталог — публичное
   чтение опубликованных статей без авторизации, создание/комментирование
   только с аккаунтом (тот же паттерн, что у `GET /routes` vs
   `POST /routes/{id}/reviews`).

### G.1 — Модель данных (backend)

Три новые таблицы, миграция `0048_articles` (следующий номер после
`0047_runtime_settings`; revision id `0048_articles` — 15 символов,
укладывается в лимит 32 символа для `alembic_version`).

**`articles`** (`Article(Base, UUIDPrimaryKeyMixin, TimestampMixin)`,
модуль `modules/content/infrastructure/models.py` — новый модуль
`content`, не запихивать в `routes`/`places`, статья не принадлежит ни
одному из них исключительно):

| Поле | Тип | Примечание |
| --- | --- | --- |
| `author_user_id` | `UUID`, FK `users.id` ON DELETE CASCADE, indexed | как `RouteReview.author_user_id` |
| `title` | `String(120)`, not null | лимит из G.0 п.4 |
| `status` | `String(32)`, not null, default `draft` | CHECK `IN ('draft','pending_review','published','rejected','deleted')` — на один статус больше, чем у отзывов (G.0 п.3) |
| `related_route_id` | `UUID`, FK `routes.id` ON DELETE SET NULL, nullable, indexed | G.0 п.5 |
| `related_place_id` | `UUID`, FK `places.id` ON DELETE SET NULL, nullable, indexed | G.0 п.5 |
| `cover_media_attachment_id` | `UUID`, FK `media_attachments.id` ON DELETE SET NULL, nullable | обложка = первая картинка первого image-блока, но кэшируем ссылкой, чтобы не искать блоки на каждый рендер карточки в ленте |
| `moderator_note` | `String(500)`, nullable | как у `RouteReview` |
| `moderated_at` | `DateTime(timezone=True)`, nullable | как у `RouteReview` |
| `published_at` | `DateTime(timezone=True)`, nullable | отдельно от `moderated_at` — момент публикации важен для сортировки ленты «новые статьи», а `moderated_at` фиксируется и на `rejected` тоже |

`CheckConstraint`: `related_route_id IS NULL OR related_place_id IS NULL`
(нельзя привязать и то, и то сразу — обеспечивает G.0 п.5 на уровне БД,
не только в application-коде). Индексы: `(status, created_at)` —
модерационная очередь (тот же паттерн, что
`ix_route_reviews_moderation_queue`); `(author_user_id, status)` — «мои
статьи»; `(related_route_id)`, `(related_place_id)` — уже частично

**`article_blocks`** (`ArticleBlock(Base, UUIDPrimaryKeyMixin)`, без

через пересборку статьи при правке):

| Поле | Тип | Примечание |
| --- | --- | --- |
| `article_id` | `UUID`, FK `articles.id` ON DELETE CASCADE, not null, indexed | |
| `position` | `Integer`, not null | порядок внутри статьи, как `RouteStop.position` |
| `block_type` | `String(16)`, not null | CHECK `IN ('text', 'image')` — сознательно только два типа на v1, не проектируем под произвольные embed-виджеты (см. текст ниже, уже был в плане) |

| `media_attachment_id` | `UUID`, FK `media_attachments.id` ON DELETE CASCADE, nullable | заполнено только когда `block_type='image'` |

— на уровне БД гарантирует, что блок не окажется наполовину текстом,
наполовину картинкой или вообще пустым. `UniqueConstraint(article_id, position)`.

**`article_comments`** (`ArticleComment(Base, UUIDPrimaryKeyMixin, TimestampMixin)`

| Поле | Тип | Примечание |
| --- | --- | --- |
| `article_id` | `UUID`, FK `articles.id` ON DELETE CASCADE, not null, indexed | |
| `author_user_id` | `UUID`, FK `users.id` ON DELETE CASCADE, not null, indexed | |
| `reply_to_comment_id` | `UUID`, FK `article_comments.id` ON DELETE SET NULL, nullable | треды, как `RouteReview.reply_to_review_id` |
| `body` | `String(2000)`, not null | тот же лимит, что у отзывов — это комментарий, не статья |
| `status` | `String(32)`, not null, default `pending_review` | CHECK `IN ('pending_review','published','rejected','deleted')` — без `draft`, комментарий пишется в один присест |
| `moderator_note` | `String(500)`, nullable | |
| `moderated_at` | `DateTime(timezone=True)`, nullable | |

Индексы: `(article_id, status, created_at)` — лента комментариев;
`(status, created_at)` — общая модерационная очередь.

**Media**: расширить CHECK-constraint `entity_type` в `media_attachments`

### G.2 — Медиа: переиспользовать, не писать заново

Новый файл `modules/content/application/article_media.py`, по образцу
`routes/application/review_media.py` практически один в один: те же
лимиты (`_MAX_BYTES = 10MB`, `_MAX_IMAGE_PIXELS = 12_000_000`,
`_MAX_IMAGE_EDGE = 2048`, EXIF/metadata strip через `PIL.ImageOps`),
тот же checksum-дедуп по `sha256`, тот же `_MAX_ARTICLE_IMAGES = 12`
(G.0 п.4). Отличие от отзывов: изображение привязывается не напрямую к
статье, а к конкретному `ArticleBlock` — порядок загрузки: (1) создать
image-блок с `media_attachment_id=null` → (2) `POST .../blocks/{id}/image`
загружает файл и проставляет `media_attachment_id` → это позволяет
клиенту сначала зарезервировать позицию блока в правильном порядке, потом
догрузить картинку (полезно при плохой связи — можно ретраить именно
загрузку файла, не пересобирая порядок блоков).

### G.4 — API-роутер

Новый `modules/content/presentation/router.py`, префикс `/articles`
(+ пара маршрутов под `/routes/{id}`, `/places/{id}`, `/me` — как отзывы
разбросаны между `routes/presentation/router.py` и

вложенного пути):

```
GET    /api/v1/articles                        — публичная лента (опц. ?related_route_id=, ?related_place_id=)

POST   /api/v1/articles                         — создать черновик (auth)
PATCH  /api/v1/articles/{article_id}             — редактировать черновик/rejected (auth, own)
POST   /api/v1/articles/{article_id}/submit      — отправить на модерацию (auth, own)
DELETE /api/v1/articles/{article_id}             — удалить свою статью (auth, own)
POST   /api/v1/articles/{article_id}/blocks/{block_id}/image   — загрузить картинку блока (auth, own)
DELETE /api/v1/articles/{article_id}/blocks/{block_id}/image   — удалить картинку блока (auth, own)
GET    /api/v1/articles/{article_id}/comments    — комментарии (published — всем)
POST   /api/v1/articles/{article_id}/comments    — оставить комментарий (auth)
DELETE /api/v1/articles/{article_id}/comments/{comment_id}  — удалить свой комментарий (auth, own, окно как у отзывов — 6 часов)
GET    /api/v1/me/articles                       — «мои статьи», все статусы включая draft
```

### G.8 — Mobile: экран создания (самая тяжёлая часть)

Многошаговый флоу, ближайший существующий аналог по сложности —
`route_builder` mobile flow (конструктор маршрута) и уже существующий
паттерн загрузки фото отзыва (upload + preview + удаление до отправки).
Экраны:

1. **Заголовок + опциональная привязка** — текстовое поле заголовка (до
   120 символов, G.0 п.4), опциональный выбор «Об этом маршруте» /
   «Об этой локации» / «Без привязки» — если экран открыт с детали
   маршрута/локации (G.9 вариант a), это поле уже предзаполнено и
   скрыто/показано как чип с возможностью убрать.
2. **Редактор блоков** — вертикальный reorderable-список блоков
   (`ReorderableListView`, стандартный Flutter-виджет, не нужна сторонняя
   зависимость): кнопка «+ Текст» добавляет пустой текстовый блок с
   `TextField` инлайн, кнопка «+ Фото» открывает `image_picker` (уже
   есть в `pubspec.yaml`), загружает через `uploadBlockImage`, показывает
   превью. Каждый блок — свайп-для-удаления или кнопка-крестик. Лимиты
   G.0 п.4 (20 блоков, 12 фото) проверяются на клиенте до отправки
   запроса, чтобы не тратить впустую аплоад.
3. **Предпросмотр** — рендерит блоки ровно тем же виджетом, что и
   финальный экран чтения (G.9) — предпросмотр не должен быть отдельной
   упрощённой версткой, иначе он будет врать о том, как это выглядит на
   самом деле.
4. **Отправка** — кнопка «Сохранить черновик» (без модерации, можно
   вернуться позже) и «Отправить на модерацию» (после этого редактирование
   блокируется до `rejected`, G.0 п.1/п.3).

Черновик должен переживать выход из экрана (свайп назад, звонок,
сворачивание приложения) — сохранять на бэкенде через
`create_article_draft`/`update_article_draft` при каждом шаге, а не
держать только в памяти виджета (иначе полчаса работы над статьёй
потеряются от одного случайного жеста навигации — ровно то, от чего уже
осознанно защищаются в `route_builder`).

## Рекомендованный порядок

```
A (2ГИС TSP/Suggest/Distance Matrix в AI)
  → B (Gemini provider + runtime-переключатель)
    → D (контекст — по факту закрывается внутри B, отдельной работы почти нет)
  → C (персонализация AI поверх существующего preferences-профиля)
→ E (sidebar иерархия + раздел конфигурации — E нужен для UI переключателя из B)
→ F (профиль: статистика)
→ G (блог/рецензии — отдельно, самый тяжёлый)
```

E технически можно делать параллельно с B (независимый CSS/шаблон), но
страница переключателя провайдера из B физически живёт в разделе
конфигурации из E — имеет смысл сделать разметку sidebar до формы
переключателя, чтобы не переверстывать.
