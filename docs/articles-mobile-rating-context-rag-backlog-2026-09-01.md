## Сводка находок (проверено в коде, не по памяти)

Прежде чем читать планы — четыре факта, которые меняют постановку задач:

1. **Рейтинг на карточке маршрута — фиктивный.** `route_hero_card.dart:656` выводит
   `'4,${9 - (route.name.length % 3)}'` — число выводится из длины названия. У модели
   `Route` на бэкенде поля рейтинга **нет вообще**, в `RouteListItemOut` его тоже нет.
   То есть это не «неправильно считается», а «не считается никак».
2. **Настоящий рейтинг существует, но только внутри отзывов.** `review_service.py:260-311`
   честно считает `average_rating` и `rating_count`, корректно исключая ответы на отзывы
   (`reply_to_review_id IS NULL`). Эти данные доходят до мобилки в
   `route_reviews_repository.dart`, но **на экране деталей не показываются** — поиск
   `averageRating` по `lib/features/routes/presentation/` не даёт ничего.
3. **Эмбеддер RAG — хеш от токенов, без семантики.** `knowledge/application/embedder.py`:
   каждый токен хешируется в слот со случайным знаком. Синонимы («гора» / «вершина»)
   попадают в разные слоты, косинусная близость между смыслово связанными текстами
   около нуля. Docstring это признаёт: «Swap to a real EmbeddingProvider later».
   Фактически векторный поиск сейчас **хуже** FTS-фолбэка, потому что FTS хотя бы делает
   русский стемминг.
4. **RAG выключен в проде.** `RAG_ENABLED` на сервере не выставлен → `False`. При этом в
   БД лежат 72 чанка, у всех 72 есть эмбеддинги (то есть проиндексировано хешем).

## G.9 — Редактор (самый объёмный шаг)

**`article_editor_screen.dart`** — блочный редактор. Ключевое решение, вытекающее из
бэкенда: **правка заменяет весь список блоков целиком** (`_replace_blocks`), поэтому
клиент держит блоки в локальном состоянии и отправляет их одним `PATCH`.

Порядок работы с картинками (продиктован API):
1. блок создаётся пустым (`block_type: image`, без файла) — `POST`/`PATCH` статьи;
2. файл грузится отдельно: `POST /articles/{id}/blocks/{block_id}/image`.

Так сделано намеренно: при плохой связи можно ретраить **только загрузку файла**, не
пересобирая порядок блоков. UI должен это использовать — показывать у блока состояние
«ожидает загрузки» и кнопку «Повторить».

**Осторожно, грабли:** `PATCH` со списком блоков **удаляет уже загруженные картинки**
тех блоков, которых нет в новом списке (бэкенд архивирует вложения и удаляет файлы).
Значит клиент обязан отправлять блоки с их `id`, а не пересоздавать список с нуля,
иначе картинки будут теряться при каждом сохранении заголовка.

Состав экрана:
- поле заголовка (до 120 символов, счётчик);
- список блоков с drag-to-reorder, добавлением текста/картинки, удалением;
- текстовый блок — до 4000 символов, счётчик;
- лимиты: 20 блоков, 12 картинок — блокировать кнопки заранее, не ловить 409;
- привязка к маршруту/локации — **или** одно, **или** другое (на бэкенде CHECK-констрейнт),
  UI должен делать выбор взаимоисключающим;
- автосохранение черновика (debounce ~2с), индикатор «Сохранено»;
- «Отправить на модерацию» с подтверждением: после отправки редактировать нельзя.

# Часть 2 — Рейтинг маршрутов

## Что сейчас (проверено)

- **Карточка каталога:** `route_hero_card.dart:656` — `'4,${9 - (route.name.length % 3)}'`.
  Фиктивное число из длины названия. Все маршруты показывают 4.7 / 4.8 / 4.9.
- **Бэкенд:** у `Route` нет поля рейтинга; `RouteListItemOut` его не отдаёт.
- **Экран деталей:** настоящий рейтинг приходит вместе со списком отзывов
  (`average_rating`, `rating_count`), но **нигде не отображается**.
- **Считается корректно** там, где считается: ответы на отзывы исключаются из среднего.

## Что делаем

### 2.1 Бэкенд: отдавать рейтинг в каталоге

Считать на лету агрегатом при выдаче списка — не денормализовать в `routes`, пока нет
доказанной проблемы с производительностью (каталог сейчас небольшой, а денормализация
требует инвалидации при каждой модерации отзыва).

- в `RouteListItemOut` и `RouteDetailOut` добавить `rating_average: float | None` и
  `rating_count: int`;
- считать одним `GROUP BY` по всем маршрутам страницы, не по одному запросу на карточку
  (тот же приём, что `_preload_user_names` в админке);
- условия те же, что уже в `review_service`: `status='published'` и
  `reply_to_review_id IS NULL`.

### 2.2 Правило «минимум одна оценка»

Пользователь: *«Минимум 1 оценка должна быть»*.

- `rating_count == 0` → `rating_average = null`;
- карточка при `null` **не показывает звезду вообще** (не «0.0» и не «—»): пустая звезда
  читается как «плохой маршрут», а это ложь про маршрут, который просто новый;
- вместо звезды — ничего, либо ненавязчивое «Нет оценок» мелким шрифтом, если дизайн
  требует заполнить место.

### 2.3 Количество оценок в деталях

Пользователь: *«в подробностях маршрута у рейтинга должно показываться в скобках
количество оценок»*.

- формат: `4,3 (12)` — среднее с одним знаком, в скобках `rating_count`;
- склонение для доступности/подписи: «12 оценок» (1 оценка / 2 оценки / 5 оценок);
- тап по рейтингу — скролл к секции отзывов.

### 2.4 Что ещё стоит решить (нужно твоё слово)

- **Байесовское сглаживание.** Маршрут с одной пятёркой обгоняет маршрут с 4.8 из 50
  оценок при сортировке по рейтингу. Классическое лечение — среднее с приором:
  `(C·m + Σ) / (C + n)`, где `m` — средняя по каталогу, `C` ≈ 5. Показывать при этом
  можно честное среднее, а сортировать по сглаженному. **Нужно только если появится
  сортировка по рейтингу** — сейчас её нет, поэтому вынес в «решить», а не в план.
- **Оценка без текста.** Сейчас оценка — часть отзыва (`body` обязателен). Если хочется
  «поставить звёзды, не писать текст» — это отдельная задача, меняет модель.

### 2.5 Тесты

- у маршрута без опубликованных отзывов `rating_average` = `null`, `rating_count` = 0;
- ответы на отзывы не влияют на среднее и не считаются в `rating_count`;
- отклонённый/удалённый отзыв выпадает из агрегата;
- виджет-тест: при `null` звезды нет; при значении — формат `4,3 (12)`;
- **отдельным тестом** зафиксировать, что фиктивной формулы больше нет.

# Часть 3 — Контекст ИИ-диалога: теги и заголовки вместо сырой истории

## Что сейчас (проверено)

- `session_service.py:100` — `_HISTORY_LIMIT = 12`: в модель уезжают **последние 12
  сырых сообщений** целиком;
- `gemini.py` дополнительно режет до `messages[-12:]`;
- сжатия нет — старше 12 сообщений контекст просто **теряется**;
- у `RoutePlanningSession` есть `constraints` (JSONB) и `confirmed_fields` — то есть
  структурированное состояние уже частично собирается, но только по жёстким полям
  (город, темп, интересы…);
- персонализация есть, но узкая: `_persisted_preferences_prior()` отдаёт максимум
  4 поля (`interests`, `pace_hint`, `with_children`, `with_pets`);
- системный промпт ~2.6К символов (~860 токенов) — уходит в каждый запрос.

## Проблема

Разговор длиннее 12 реплик теряет начало. Пользователь на 15-й реплике говорит «давай
как обсуждали», а модель этого уже не видит. При этом гнать всю историю целиком нельзя —
у нас жёсткий бюджет времени (см. историю с 20с таймаутом мобилки) и квота на бесплатном
ключе Gemini.

## Что делаем

### 3.1 Структурированное резюме сессии вместо сырых реплик

Новое поле `RoutePlanningSession.context_digest` (JSONB, миграция `0049`):

```json
{
  "topics": ["Ай-Петри", "канатная дорога", "обед в Мисхоре"],
  "decisions": ["едем на машине", "без детей", "1 день"],
  "rejected": ["пешие маршруты — тяжело", "Ласточкино гнездо — уже были"],
  "open_questions": ["нужен ли обед в маршруте"],
  "updated_after_message_seq": 14
}
```

**Ключевое отличие от «просто сохранять контекст»:** это не сжатая история, а **список
фактов**. `rejected` тут не менее важен, чем `decisions` — без него модель на 20-й
реплике снова предложит то, что человек уже отверг, и это самый заметный признак
«тупого» бота.

### 3.2 Как наполняется

Два варианта, у каждого своя цена:

**(а) Отдельным вызовом модели** — после каждых N реплик просить модель обновить дайджест.
Точнее, но это +1 запрос к Gemini на каждые N реплик, а квота 20/сутки на модель.
**Не рекомендую при текущем ключе.**

**(б) Тем же вызовом, дополнительным полем в JSON-ответе.** Модель и так возвращает
структурированный JSON (`assistant_text`, `constraint_patch`, `ask_field`…). Добавляем
необязательное `context_digest_patch`, которое дописывает новые теги/решения. Ноль
дополнительных запросов, но требует правки промпта и парсинга.

Тот же механизм переиспользуется в §4.8 для `search_queries` — оба поля едут в одном
ответе, так что правку промпта и парсера стоит делать один раз на оба.

**Рекомендация:** (б). При исчерпанной квоте каждый лишний вызов — это отказ пользователю.

### 3.3 Что уезжает в модель

```
systemInstruction = CHAT_SYSTEM_PROMPT
                  + "Известно: " + constraints (как сейчас)
                  + "Из разговора: " + context_digest   ← новое, компактно
                  + "О пользователе: " + user_profile   ← новое, см. 3.4
contents = последние 6 сырых реплик (было 12)
```

Сырых реплик станет **меньше** (6 вместо 12), потому что суть уже в дайджесте. Это
одновременно экономит токены и **удлиняет** эффективную память: дайджест покрывает всю
сессию, а не последние 12 сообщений.

### 3.4 Расширенная персонализация

Сейчас передаётся 4 поля. Добавить (всё уже есть в БД, новых таблиц не надо):

| Сигнал | Откуда | Зачем модели |
| --- | --- | --- |
| Имя | `User.display_name` | обращаться по имени |
| Звание | `TravelRank` | «опытный путешественник» → меньше базовых объяснений |
| Пройденные маршруты | `RouteExecution` (уже считается для профиля, Workstream F) | не предлагать пройденное |
| Избранное | `favorites` | понимать вкус |
| Скипы в свайпере | `RouteRecommendationFeedback` | не предлагать отвергнутое |
| Стиль общения | новое поле профиля | тон (см. `ai-personality-style` в памяти) |

**Ограничение по объёму:** не больше ~600 символов на весь профильный блок, иначе он
съест бюджет. Списки маршрутов — только названия, максимум по 5, и только те, что
релевантны текущему городу.

**Приватность:** телефон, email и точные координаты дома в промпт не уходят никогда.
Стоит закрыть это тестом, а не только договорённостью.

### 3.5 Тесты

- дайджест переживает выход за 12 реплик: факт с 3-й реплики влияет на 20-ю;
- `rejected` реально доезжает до промпта;
- профиль обрезается по лимиту и не содержит PII (телефон/почта) — отдельный тест;
- пустой профиль не добавляет в промпт пустых блоков.

- **RAGAS.** Метрики RAGAS считаются LLM-судьёй — это снова квота. Наш вариант — в §4.9.

**Одна их идея адаптируется, а не копируется:** у них `retrieve_parent_chunks` — это
**инструмент агента**, то есть лишний round-trip к модели, когда та решит, что контекста
мало. У нас родителя надо подтягивать **автоматически** вместе с попаданием в ребёнка,
на стороне SQL. Тот же результат, ноль дополнительных вызовов модели.

## Что делаем

### 4.1 Настоящие эмбеддинги

`EmbeddingProvider` уже объявлен как `Protocol` — точка расширения на месте.
Три варианта:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Локальная `sentence-transformers`** (`paraphrase-multilingual-MiniLM-L12-v2`, 384-d) | **размерность совпадает — миграции схемы не нужно**; ноль расхода квоты; ноль сети в горячем пути; переиндексация бесплатна и повторяема | ~0.5ГБ веса + ~1ГБ RSS с торчем; нужен сервер, где эта память есть |
| **Gemini `text-embedding-004`** | не нужен свой хостинг; качественный русский | расход квоты; сеть на каждый запрос; размерность не 384 → миграция |
| **LM Studio** | уже есть в контуре как провайдер | нужна запущенная LM Studio, на сервере её нет |

**Рекомендация (пересмотрена 2026-09-02 под переезд на сервер 8ГБ):
локальная `paraphrase-multilingual-MiniLM-L12-v2`.**

Раньше здесь стояла Gemini — **и единственной причиной был RAM 477МБ на
`crimeatrip-test`**. Как только этого ограничения нет, локальный вариант выигрывает по
всем остальным пунктам:

- **384-d совпадает с текущей колонкой `vector(384)`** — миграция `0050` на смену
  размерности **не нужна вообще**, только переиндексация. Это самый дешёвый путь из всех
  трёх;
- **ноль расхода квоты.** У нас бесплатный ключ Gemini ~20 запросов в сутки, и вся
  архитектура из Части 3 и §4.0 выкручивается вокруг этого лимита. Локальный эмбеддер
  убирает RAG из этого уравнения целиком;
- **переиндексация становится бесплатной и повторяемой.** Это прямо снимает риск с §4.5:
  можно свободно перебирать нарезку из §4.7 и мерить по набору из §4.9, а не считать
  каждый прогон в квоте;
- **нет сетевого round-trip в горячем пути.** У мобилки 20-секундный таймаут; эмбеддинг
  короткого запроса на CPU EPYC — единицы-десятки миллисекунд против сетевого вызова.

Оговорки, которые надо учесть при реализации:

- держать модель **загруженной один раз** в процессе (или отдельным маленьким сервисом),
  а не грузить на запрос — иначе первый запрос будет секунды;
- `torch` + веса — это ~2–3ГБ на диске, заложить при выборе размера диска;
- если качество на нашем русском корпусе окажется недостаточным (меряем набором из §4.9,
  а не на глаз) — следующий шаг **не** Gemini, а более крупная локальная модель
  (например Qwen3-Embedding из §4.0). Тогда размерность перестанет совпадать и миграция
  всё-таки понадобится — но только по доказанной причине.

Старые хешевые векторы в любом случае выбрасываем и переиндексируем.

**Обязательно:** хранить `embedding_model` в строке (поле уже есть) и **отказываться
искать**, если модель запроса не совпала с моделью чанков. Иначе после смены модели
поиск начнёт молча возвращать мусор — самый неприятный вид поломки, потому что он
выглядит как работающий.

### 4.2 Гибридный поиск вместо «вектор, иначе FTS»

Сейчас FTS — аварийный фолбэк (`except → rows = []`). После починки эмбеддингов стоит
сделать их равноправными: вектор ловит смысл, FTS ловит точные имена собственные
(«Ай-Петри», «Массандровский дворец»), где вектор как раз слабее.

Слить через Reciprocal Rank Fusion (`score = Σ 1/(k + rank)`, `k≈60`) — не требует
калибровки весов между разными шкалами, в отличие от линейной комбинации.

### 4.3 Порог релевантности

Сейчас `min_score: float = 0.0` — «0 disables thresholding», то есть в промпт летят
top-k **любых** чанков, даже нерелевантных. С настоящими эмбеддингами появится
осмысленная шкала → выставить порог (подобрать эмпирически, ориентир **0.4–0.6**
косинуса: 0.4 — рабочее значение `RETRIEVAL_SCORE_THRESHOLD` в
`agentic-rag-for-dummies`, см. §4.0) и отдавать **пустой** результат, если ничего не
прошло. Пустой контекст лучше нерелевантного: нерелевантный чанк модель попытается
использовать. Калибровать по набору из §4.9, а не на глаз.

### 4.4 Наполнение базы

72 чанка на весь Крым — мало. Отдельная задача (нужны источники с приемлемой лицензией —
поле `license` в модели уже есть). Тут важно: **пока чанков мало, RAG лучше не включать**
— он будет отдавать нерелевантное просто потому, что релевантного нет.

### 4.5 Порядок

1. **Eval-набор (§4.9) — первым.** Иначе замену эмбеддера нечем доказать: «стало лучше»
   на глаз не отличается от «стало иначе».
2. Заменить эмбеддер + миграция размерности + переиндексация чанков.
3. Прогнать eval-набор до/после — зафиксировать hit@5 обеими цифрами в этом документе.
4. Иерархические чанки (§4.7) + переиндексация.
5. Гибридный поиск + порог, откалиброванный по набору.
6. Переписывание запроса (§4.8) — оно осмысленно только когда поиск уже не мусорит.
7. Наполнить базу.
8. **Только потом** включать `RAG_ENABLED=true` на тесте.

### 4.6 Тесты

- запрос синонимом находит чанк («вершина» → чанк про «гору») — это ровно то, что
  сегодня не работает и что доказывает замену эмбеддера;
- при несовпадении `embedding_model` поиск возвращает пусто, а не мусор;
- порог отсекает нерелевантное;
- RAG-сбой не роняет чат (сейчас это уже так — `except` вокруг всего блока, сохранить);
- поиск по ребёнку возвращает тело родителя, а не ребёнка (§4.7);
- переписанный запрос сохраняет имя собственное дословно (§4.8).

### 4.7 Иерархические чанки: ищем по детям, отвечаем родителями

Взято из `agentic-rag-for-dummies` (§4.0), адаптировано под pgvector.

**Проблема, которую это решает.** Размер чанка — компромисс: мелкий точнее ищется
(меньше «размывается» эмбеддинг), крупный лучше отвечает (в нём есть контекст). Сейчас у
нас один размер на обе задачи — секция по markdown-заголовку до `_MAX_CHUNK_WORDS = 400`
(`chunker.py:16`).

**Что делаем.** Родитель — то, что `chunker.py` режет сейчас (менять его логику не надо,
секция по заголовку — это уже правильная семантическая единица). Ребёнок — нарезка
родителя фикс-окном с перекрытием.

- ориентиры от них: ребёнок **500 символов, перекрытие 100**, родитель **2000–4000**;
  наши текущие ~2800 символов на секцию в этот диапазон уже попадают, так что менять
  верхнюю границу не придётся — только добить слишком короткие секции слиянием и
  разрезать переросшие, как делают они;
- схема: `knowledge_chunks.parent_chunk_id` (self-FK, `NULL` у родителя) + частичный
  индекс. Отдельную таблицу не заводить — родитель и ребёнок отличаются одним полем;
- **эмбеддинг считается только у детей**, у родителей `embedding IS NULL`. Это заодно
  экономит вызовы эмбеддера при ингесте;
- в `retriever.py`: искать по детям, затем **одним `JOIN` подтянуть тело родителя** и
  дедуплицировать по `parent_chunk_id` (два ребёнка одного родителя → один результат).
  Именно здесь мы расходимся с источником: у них это инструмент агента с отдельным
  round-trip к модели, у нас — часть того же SQL-запроса;
- порог (§4.3) применяется к скору **ребёнка**, а в промпт уезжает текст родителя.

### 4.8 Переписывание запроса перед поиском

Тоже оттуда, и это самая дешёвая из взятых идей, потому что **не добавляет ни одного
вызова модели**: складывается в тот же structured-JSON-ответ, через который §3.2(б)
собирает `context_digest_patch`.

Сейчас в ретривер уходит последняя реплика как есть. «А как туда добраться?» без
подстановки — это запрос без единого содержательного слова, любой поиск по нему вернёт
мусор независимо от качества эмбеддера.

Добавляем в JSON-ответ модели необязательное `search_queries: list[str]`:

- разрешать ссылки на предыдущий контекст → самодостаточный запрос («а туда как
  добраться?» → «как добраться до Ай-Петри»);
- разбивать составной вопрос максимум на **3** подзапроса (их ограничение, разумное:
  больше подзапросов — больше чанков в промпте, а бюджет у нас жёсткий);
- **имена собственные, числа и названия переносить дословно**, без синонимизации —
  «Ай-Петри», «Массандровский дворец», «№5». Это прямо прописать в промпте: перефразировка
  имени собственного ломает как раз то плечо гибрида (FTS), которое на именах сильнее
  векторного;
- поле пустое/отсутствует → ищем по сырой реплике, как сейчас (деградация без поломки).

Искать по каждому подзапросу и слить результаты тем же RRF, что и в §4.2.

### 4.9 Оценка качества: маленький фиксированный набор

У нас сейчас **нулевая** оценка ретривера. Источник использует RAGAS, но её метрики
считает LLM-судья — это снова квота, поэтому берём идею, а не инструмент.

- `tourism-backend/tests/data/rag_eval.jsonl` — **20–30 реальных вопросов про Крым**,
  у каждого руками проставлены `expected_doc_ids` (какие чанки обязаны найтись).
  Составить один раз, руками, по существующим 72 чанкам;
- метрики — **чисто ретривальные, без единого вызова модели**: `hit@5` (нужный чанк в
  топ-5) и `MRR`. Их достаточно, чтобы доказать замену эмбеддера, и они считаются
  мгновенно и детерминированно;
- гонять как обычный pytest-тест с порогом-регрессией (например, `hit@5 >= 0.7` после
  замены эмбеддера), а не как разовый скрипт;
- **зафиксировать в этом документе цифры «до» и «после»** — сейчас утверждение «FTS
  объективно лучше хеш-вектора» логически обосновано, но не измерено.

Набор нужен раньше самой замены (см. §4.5), иначе непонятно, что именно улучшилось.

### 5.1 Четыре параметра спрашиваются у человека и молча игнорируются

Причём мобилка их именно **спрашивает**: `route_match_screen.dart:377-381` собирает
бюджет, «когда» и «избегать толп» в расширенном режиме и отправляет на бэкенд.
Человек заполняет поля, которые ни на что не влияют.

Комментарий в схеме говорит «accepted now, scored when present» — но `when present`
так и не наступило.

**Что делать — сначала решить, а потом кодить:**
- `avoid_crowds` — данных о посещаемости у нас нет. Прокси: штрафовать маршруты с
  самыми популярными точками (по числу `RouteExecution`/избранных). Либо **убрать
  галку из формы**, пока нечем её обеспечить.
- `budget_amount` / `paid_ok` — у `Place` нет цен. Пока нет — убрать из формы.
- `day_kind` (выходной/будний) — влияет на расписание точек; в `PlaceSchedule` данные
  есть, можно штрафовать маршруты с закрытыми в этот день точками. Это реализуемо.

**Принцип: либо параметр влияет на результат, либо его нет в форме.** Спрашивать и
игнорировать — хуже, чем не спрашивать: человек считает, что подбор его учёл.

### 5.2 География через подстроки при живом PostGIS

`_city_score` сравнивает **строки**: `needle in loc or loc in needle`. Последствия:

- Мисхор, Гаспра, Кореиз — фактически Ялта, но для алгоритма это `0.05`
  («город не совпал»), после чего срабатывает ещё и общий штраф `score *= 0.55`.
- «Ялта» найдёт «Ялтинский горно-лесной заповедник» — это как раз повезло.
- Опечатка или другое написание («Севастополь» / «Севастопіль») — мимо.

При этом у нас **PostGIS с координатами точек и геометрией маршрутов**, уже
используемый в других местах. Считать близость строками, имея пространственную БД, —
самая крупная упущенная возможность в этом алгоритме.

**Что делать:** `_city_score` → расстояние от центра города до старта маршрута
(или до ближайшей точки). Плавная шкала вместо ступеньки:
`1.0` при < 5 км, линейно вниз до `0.2` на 60 км, ниже — отсечка. Название оставить
как фолбэк, если у города нет координат.

### 5.3 Чем больше интересов выбрал человек, тем ниже скор у всех маршрутов

`_interests_score` возвращает `hits / len(interests)`. Выбрал один интерес и он
совпал — `1.0`. Выбрал пять, совпало два — `0.4`, и это **лучший** маршрут в выдаче.

То есть подробный запрос давит всю выдачу вниз, вплоть до того, что ни один маршрут
не дотягивает до `IDEAL_THRESHOLD` и человек получает пустую полосу «идеально
подходят». Это ровно наоборот тому, как должно быть: больше информации о
пользователе — лучше подбор, а не хуже.

**Что делать:** насыщающая функция вместо доли. Например
`1 - exp(-k · hits)` (`k ≈ 0.8`): 1 совпадение → 0.55, 2 → 0.80, 3 → 0.91.
Совпадения **добавляют**, несовпадения не штрафуют. Плюс учитывать, что совпало по
таксономии (сильный сигнал), а что по ключевым словам (слабый) — сейчас они
равнозначны.

### 5.4 Порог «идеально» почти не отличается от «ничего не знаем»

Каждая под-оценка при отсутствии сигнала возвращает нейтральные `0.5`. Маршрут, про
который неизвестно **ничего**, получает итог около `0.5` — при `IDEAL_THRESHOLD = 0.55`.
Планка «идеально подходит» стоит чуть выше уровня «данных нет».

**Что делать:** развести «нейтрально» и «подтверждённо совпало». Варианты:
- считать только по тем сигналам, которые реально известны (нормировать вес на
  сумму весов **непустых** под-оценок) — тогда неизвестность не подтягивает к 0.5;
- отдельно считать `confidence` (доля известных сигналов) и не пускать в `ideal`
  кандидатов с низкой уверенностью, даже при высоком скоре.

Второе честнее: маршрут с одним совпавшим полем из девяти не «идеальный», он
«непонятный».

### 5.5 Выдача может состоять из трёх почти одинаковых маршрутов

`partition_scored` берёт просто топ-3 по скору. Три маршрута по одному городу с
одинаковым набором точек — законный результат.

**Что делать:** MMR-подобный отбор — при выборе следующего кандидата штрафовать за
пересечение по точкам/категориям с уже выбранными. Формула:
`итог = score − λ · max(similarity с уже выбранными)`, `λ ≈ 0.3`.
Похожесть — доля общих `place_id` или `category_slugs`.

### 5.6 Отбор кандидатов сломается молча при росте каталога

`_load_candidates` — `ORDER BY Route.name LIMIT 200`. Сейчас маршрутов 33, всё
влезает. Когда станет больше 200, в подбор будут попадать **первые 200 по алфавиту**,
а остальные перестанут существовать для алгоритма. Без ошибки, без лога.

**Что делать:** предфильтрация в SQL до лимита — по региону (уже есть), по
географической близости к городу (см. 5.2), по жёстким несовместимостям
(транспорт, дети/питомцы при явном требовании). Скорить уже отобранное.
Плюс лог, когда лимит реально сработал.

### 5.7 Нет обратной связи

Скоринг ничему не учится: какие карточки человек открыл, какие проигнорировал, какой
маршрут в итоге прошёл — на подбор не влияет. При этом `RouteRecommendationFeedback`
для свайпера уже собирается.

**Что делать (не сразу, но заложить):** логировать показы и клики подбора, потом
использовать как мягкий приор. Сначала — просто накопить данные.
