- Статус: принято
- Дата: 2026-08-23
- Связано: [ADR-003](ADR-003-postgresql-postgis.md),

## Контекст

AI-чат подбора работает end-to-end (топик-гард, allowlist-инструменты,
structured turn, match-first, proposal→accept), но **охват подбора узкий**.
Замер на test-контуре 2026-08-23 показал, что причина не в AI-слое, а в
данных под ним.

### Заполненность `places` (5020 записей)

| Поле | Заполнено |
| --- | --- |
| `place_categories` (таксономия) | **100%** |
| `accessibility` | 99.6% |
| `locality_id` | **1.7%** |
| `payment_status != unknown` | 1.4% |
| `short_description` / `difficulty` | 0.4% |
| `description` | 0.1% (3 места) |
| `seasonality` | 0.02% |
| `recommended_visit_minutes` | **0%** |
| `access_transport`, `parking_available`, `price_*` | **0%** |
| `typical_crowding` | 100% `unknown` |
| `content_enrichment_status` | 100% `missing` |

### Три следствия, которые это порождает

1. **Веса скоринга — декорация.** В `scoring.py` восемь взвешенных
   компонентов; пять из них (`_season_score`, `_pace_score`,
   `_transport_score`, `_party_flags_score`, частично `_duration_score`)
   читают колонки с заполненностью ~0% и всегда возвращают нейтральный
   дефолт 0.4–0.5. Реально работают только совпадение города по подстроке
   и keyword-стемминг интересов по словарю из 10 слов.

2. **Единственный сильный сигнал игнорируется.** Категории проставлены у
   **100%** мест (15 slug-ов: `nature`, `museum`, `fortress`, `viewpoint`,
   `cave`, `winery`, …), но ни `scoring.py`, ни `place_picker.py` не
   читают `place_categories`. Вместо этого выполняется поиск подстроки
   «гор» по свободному тексту, заполненному на 0.1%.
   `RouteMatchCandidate` вообще не имеет поля категории.

3. **Фильтр по городу почти всегда деградирует.** `locality_id` есть у
   1.7% мест, поэтому `place_picker.py` уходит в ветку
   `ILIKE '%город%'` по name/address. Это корневая причина легов «218 км
   пешком»; гео-chain-select лечит симптом.

### Смежные ограничения

- Мы **выбрасываем уже скачанные данные**: в `source_payload` лежат
  `description` (785 мест), `ele` (773), `wikipedia` (251),
  `website` (156), `opening_hours` (114), `surface` (107), `fee` (52),
  `access` (43), `ruins` (35). `osm_import.py` не переносит их в
  типизированные колонки.
- `localities` в БД всего **8**, а city-picker в чате предлагает 10 —
  для «Саки» и «Керчь» нет строки `Locality`, они не сматчатся никогда.
- Эмбеддер `hash-v1` (`knowledge/application/embedder.py`) —
  bag-of-tokens хеш, **не семантический**. Текущий «векторный поиск» это
  keyword-матчинг в векторной обёртке.
- `RoutingProvider` в проде — `stub` (haversine × 1.35). Дороги не
  моделируются; для Крыма с серпантинами расхождение с реальностью
  кратное.

## Решение

Принимаем принцип **data-first**: до расширения набора параметров в
чате и до новых AI-фич приоритет отдаётся наполнению и типизации данных,
на которых работает существующий движок.

1. **`source_payload` — сырой SoT, типизированные колонки — рабочий
   контракт.** Обогащение переносит теги OSM в колонки `places`
   отдельным идемпотентным шагом; `source_payload` не мутируется и
   остаётся источником для повторного прогона.

2. **Таксономия — первичный сигнал подбора.** `place_categories`
   становится основным входом скоринга; свободный текст — вторичным.
   `RouteMatchCandidate` и `PickedPlace` получают категории.
   `INTEREST_KEYWORDS` остаётся, но как fallback, а не как основной путь.

3. **`locality_id` заполняется геометрически.** Бэкфилл через PostGIS
   (ближайшая `Locality` в радиусе), а не по подстроке имени. Список
   `localities` расширяется до набора, который предлагает UI.

4. **Семантика требует настоящей модели.** Векторный матчинг мест и
   маршрутов не расширяется на `hash-v1`. Сначала заменяем эмбеддер на
   семантический (dim фиксируется миграцией), затем распространяем
   вектора на `places` / `routes`.

5. **Динамический контекст — отдельный порт, никогда не блокирующий.**
   Погода, состояние дорог и закрытия локаций получают порт по образцу
   `RoutingProvider` (application-порт + инфраструктурный адаптер +
   кеш + деградация). Недоступность внешнего источника **не** ломает
   generate: маршрут строится без динамического слоя с пометкой, как
   `ai_unavailable_fallback_used` сегодня.

6. **Модульный монолит сохраняется** (ADR-001). Порядок будущего
   выделения определяется профилем ресурсов, а не модой на домены:
   `routing/OSRM` → `AI inference` → `ingest/enrichment workers`. Все
   три уже за портами либо вынесены в скрипты. Kafka (ADR-005) не
   поднимается до появления первой реальной асинхронной потребности.

## Альтернативы

### Расширять параметры чата сейчас

Отклонено: новые параметры упрутся в те же колонки с нулевой
заполненностью и увеличат долю компонентов скоринга, возвращающих
нейтральный дефолт.

### Отдать обогащение целиком LLM

Отклонено как основной путь: галлюцинации в часах/ценах/закрытиях
недопустимы (см. ADR-006). LLM применяется к narrative-полям
(`description`, `short_description`) с обязательным review-gate;
фактические поля берутся из OSM/эталонных источников.

### Сразу микросервисы

Отклонено: 5020 мест, 32 маршрута, 25 сессий. Распил даст
распределённый монолит без выигрыша. Границы уже зафиксированы портами.

## Последствия

- Требуется миграция под новые колонки (`elevation_meters`,
  `opening_hours_raw`, `website_url` уже есть, и т.д.) и под смену
  размерности эмбеддингов.
- Скоринг по категориям изменит выдачу подбора — нужны golden-тесты
  до и после, иначе регрессия незаметна.
- Бэкфилл `locality_id` меняет поведение `place_picker` для всех
  городов; «218 км» должно уйти как класс, а не точечно.
- Динамический слой добавляет внешние зависимости — обязателен кеш и
  бюджет времени, иначе generate станет медленным и хрупким.

## Security

- Внешние источники (OSM, Wikimedia, Wikidata, погода) — **untrusted**:
  host-allowlist на каждый запрос, валидация схемы ответа, лимит
  размера, fail-closed по лицензиям (как в `photo_import.py`).
- Обогащённые тексты в RAG остаются untrusted DATA (prompt injection).
- Публикация не автоматическая: обогащение не меняет
  `publication_status`; review-gate обязателен для `proposed_slug`,
  `description` и `is_cover`.
- Динамический контекст не является SoT для закрытий и цен — только
  сигнал ранжирования и предупреждение пользователю.
