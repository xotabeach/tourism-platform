# SEC-EX-2026-001 — Cleartext OTP code in local/test databases

Status: **active** · Opened: 2026-07-31

## Finding

`authentication-and-token-security.md` requires OTP codes to be stored as a
digest only. `AUTH_OTP_STORE_DEBUG_CODE` writes the generated code in cleartext
to `auth_otp_challenges.debug_code` and
`auth_phone_change_challenges.debug_code`.

## Business reason

No SMS provider is connected yet, so a code that is only stored as a SHA-256
digest cannot be delivered to anyone. Without a readable copy the phone-OTP
login cannot be exercised on the shared test contour at all, and the only
alternative — accepting any code — removes verification and rate limiting
entirely, which is strictly worse.

## Scope and compensating controls

- Enabled only for `APP_ENV` `local` and `test`. `validate_settings` refuses to
  start the process when the flag is set in staging or production.
- `AUTH_OTP_ACCEPT_ANY` now defaults on for `local` only, so the test contour
  performs real verification against the digest with rate limits active.
- The cleartext copy never leaves the database: it is not returned by any
  endpoint, not logged, and not exposed in any DTO.
- Codes expire after 10 minutes and are single-use (`consumed_at`).
- Test data only. The test contour holds no production personal data.
- Regression tests: `tests/security/test_otp_config_security.py`,
  `tests/security/test_otp_challenge_storage.py`.

## Residual risk

Read access to a local/test database yields live OTP codes for accounts on that
contour, which are test accounts. Accepted.

## Remediation plan

Connect the SMS provider (Phase 6 remainder), deliver the code over SMS, then
delete the `debug_code` columns in a follow-up migration and remove the setting.
Independently, move OTP digests to a keyed HMAC so a database read alone cannot
recover a four-digit code by brute force.
