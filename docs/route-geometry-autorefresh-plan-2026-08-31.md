# План: автотриггер и крон-актуализация геометрии маршрутов

Дата: 2026-08-31 (следующая сессия). Контекст и мотивация — в переписке
2026-08-30: сейчас геометрия (`Route.distance_meters`,
`RouteRoutingSnapshot.*`, полилиния для статичной карты) считается через 2ГИС
**один раз** и лежит в БД, но пересчёт — исключительно ручной
(`scripts/backfill_route_geometry.py`). Если у маршрута меняются точки/их
координаты после публикации, геометрия молча устаревает: карта и дистанция
в UI продолжают показывать старые данные, ничего не сигналит о рассинхроне.

Нужны две независимые части: (1) автотриггер при создании/правке маршрута,
(2) крон, который находит и пересчитывает устаревшее без ручного участия.

## Ограничения, которые определяют архитектуру

- **2ГИС demo-key: 5 запросов/минуту**, temporary block при превышении.
  Значит очередь **обязана** сериализовать вызовы с интервалом ≥12с
  (уже видели на практике — троттлинг 15с между маршрутами в
  `backfill_route_geometry.py`), а не дергать 2ГИС напрямую из HTTP-хендлера
  создания маршрута.
- **Демо-key: маршрут до 50 км.** Уже есть маппинг 403 → `route_too_long`
  (`two_gis_routing.py::_http_error_code`) — автотриггер должен так же не
  считать это "ошибкой инфраструктуры", а помечать маршрут статусом
  "geometry unavailable: too long" и не ретраить бесконечно.
- **Circuit breaker уже есть** (`_TwoGisCircuitBreaker`) — процессный, не
  переживает рестарт и не шарится между воркерами напрямую. Фоновый воркер
  крона и веб-процесс — разные процессы, значит нужно либо (a) считать
  геометрию только в одном месте (выделенный worker/one-off контейнер), либо
  (b) вынести breaker-состояние в Redis, если считаем из нескольких мест.
  Проще — вариант (a): одна очередь, один consumer.
- **Никогда не гонять 2ГИС в CI** и не логировать ключ (existing constraint,
  `TWO_GIS_API_KEY` только из `.env` бэкенда) — воркер это тоже backend-код,
  условие не меняется.

## Часть 1 — Автотриггер при создании/изменении маршрута

**Что считается "изменением, требующим пересчёта":** создание маршрута;
добавление/удаление/переупорядочивание `RouteStop`; смена координат точки
места (`Place.location` меняется — это редко, но бывает при модерации
places). НЕ считается: правки текста (name/description), смена
`publication_status`/`visibility` без изменения точек.

**Механизм — не встраивать вызов 2ГИС в request-цикл создания маршрута.**
Вместо этого:

1. Новая таблица `route_geometry_refresh_queue` (или переиспользовать
   существующий Redis, если для этого масштаба хватит простого списка —
   но таблица честнее: переживает рестарт Redis, видна в админке для
   диагностики "почему у маршрута нет карты").
   Поля: `route_id`, `reason` (`created`/`stops_changed`/`place_moved`),
   `enqueued_at`, `attempts`, `last_error`, `status`
   (`pending`/`in_progress`/`done`/`failed_permanent`).
2. Точки постановки в очередь (application-слой, не router):
   - `route_builder` / `routes` create-flow — после коммита нового маршрута
     с непустыми стопами;
   - место, где меняются `RouteStop` (add/remove/reorder — вероятно,
     admin-правки маршрута и/или route edit API, если он есть у
     владельца);
   - место, где обновляется `Place.location` (places moderation service) —
     enqueue для всех маршрутов, где это место есть в стопах (нужен
     обратный запрос по `route_stops.place_id`).
   Ставить в очередь идемпотентно (`ON CONFLICT DO NOTHING` по
   `route_id` + `status=pending`, чтобы не копить дубли при частых правках).
3. **Отдельный consumer**, не HTTP-воркер: скрипт вроде
   `scripts/refresh_route_geometry_worker.py`, который:
   - забирает pending-записи пачками с уважением к 5 req/min (тот же
     троттлинг, что в backfill-скрипте);
   - переиспользует `two_gis_routing.py` provider + `reset_two_gis_circuit()`
     между маршрутами, как уже делает `backfill_route_geometry.py`;
   - на `route_too_long`/`routing_unreachable` помечает `failed_permanent`
     с `last_error` (не ретраит бесконечно — это не транзиентная ошибка);
   - на транспортных ошибках — `attempts += 1`, назад в `pending` с
     экспоненциальной паузой (макс. 3 попытки).
   Держать этот воркер long-running под supervisord/systemd на VPS (по
   образцу того, как уже держим `redis`/`postgres` в compose) — polling
   очереди раз в 12-15с, а не отдельный cron per-item (крон для "актуализации
   устаревшего", не для "разбора очереди новых").

**Почему не сделать синхронно в request-хендлере:** маршрут с 10 точками
даст >10 запросов к 2ГИС (routing + возможно re-geocode) — при лимите 5/мин
это полминуты+ на один HTTP-запрос создания маршрута, и один активный
пользователь исчерпает лимит для всех остальных. Асинхронная очередь —
не оптимизация, а необходимость при demo-key лимитах.

## Часть 2 — Крон-актуализация устаревшего

Отдельная забота: маршрут молчаливо устарел (например, `Place.location`
поменяли, но забыли/не успели поставить в очередь; или маршрут был создан до
того, как автотриггер появился — вся текущая база 39 маршрутов). Крон это
подчищает, вне зависимости от того, сработал ли автотриггер.

1. **Критерий устаревания**, дешёвый SQL-чек без похода в 2ГИС:
   `route.geometry_computed_at IS NULL` (новое поле — когда геометрия
   последний раз реально посчитана) **ИЛИ**
   `max(route_stop.updated_at) > route.geometry_computed_at` **ИЛИ**
   `max(place.updated_at) FOR places IN route.stops > route.geometry_computed_at`.
   Нужно новое поле `Route.geometry_computed_at` (миграция) — сейчас нет
   явного маркера "когда геометрия в последний раз была верна", есть только
   общий `updated_at` маршрута, который меняется и от неотносящихся правок.
2. **Скрипт** `scripts/refresh_stale_route_geometry.py --apply` (вариант:
   расширить существующий `backfill_route_geometry.py` флагом
   `--stale-only`, чтобы не плодить дублирующую логику подключения/экспорта)
   — находит устаревшие маршруты по критерию выше и **ставит их в ту же
   очередь `route_geometry_refresh_queue`**, что и автотриггер (не считает
   сам — переиспользует consumer из части 1, чтобря не было двух мест с
   троттлингом и circuit breaker).
3. **Cron на хосте**, по образцу уже работающих
   (`run-recommendation-decks.sh`, retention-cron из
   `production-backend-deploy-runbook.md`): wrapper + `flock`, лог в
   `/var/log/`, разумная частота — раз в сутки достаточно (геометрия дорог
   не меняется ежечасно; исключение — реально закрытые/появившиеся дороги,
   для этого уже есть отдельный `RoadEvent`/`import_terrain_features.py`
   контур, не смешивать).

## Наблюдаемость

- Добавить в новую админ-секцию (уже есть паттерн read-only ModelView,
  `admin/presentation/views.py`) вьюху для
  `route_geometry_refresh_queue` — чтобы видеть "почему у этого маршрута нет
  карты" без похода в psql (ровно то, что я вручную делал сегодня SQL-
  запросами при диагностике колоды рекомендаций — эта вьюха закрыла бы то же
  самое для геометрии).
- Метрика/лог на `failed_permanent` — если таких начинает расти много,
  вероятно демо-key лимит по километражу (50 км) начинает резать заметную
  долю каталога, сигнал на разговор про платный ключ или Flutter SDK.

## Порядок работы (когда возьмёмся)

1. Миграция: `Route.geometry_computed_at`, таблица
   `route_geometry_refresh_queue`.
2. `refresh_route_geometry_worker.py` — переиспользует троттлинг/circuit
   breaker логику из `backfill_route_geometry.py` (возможно, стоит вынести
   общий throttled-runner в отдельный модуль, раз им пользуются 3 места:
   backfill, автотриггер-consumer, cron-consumer — по факту это один и тот
   же consumer, просто разные источники записи в очередь).
3. Точки enqueue в route create / stops edit / place location edit.
4. `--stale-only` в существующем backfill-скрипте (или новый скрипт) для
   крона.
5. Cron на хосте + admin-вьюха на очередь.
6. Тесты: enqueue идемпотентен (двойной create не даёт двух pending-записей);
   `route_too_long` → `failed_permanent`, не ретраится; троттлинг соблюдает
   интервал между вызовами (можно мокать sleep и считать интервалы вызовов).

## Что НЕ делаем в этом заходе

- Не переносим breaker/circuit state в Redis — single-consumer архитектура
  снимает необходимость.
- Не считаем геометрию синхронно нигде.
- Не трогаем Flutter SDK путь — по-прежнему открытый вопрос, не блокирует
  это план.
